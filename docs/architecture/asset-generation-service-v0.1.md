# Fibre asset generation service v0.1

## Purpose

Define a provider-neutral asynchronous service for generating presentation and other derived assets without making media-generation machinery part of Thread authority or part of a cloud-specific application contract.

Thread Presentation is the first caller. The service itself is general Fibre backend infrastructure/application logic.

The architectural lock is:

```text
application-domain projection
  Thread Presentation today
  other Fibre domains later
        |
        v
admissible AssetGenerationJob
        |
        v
AssetGenerationService
        |
        +--> InfraDriver.workflows
        |       durable asynchronous execution
        |
        +--> MediaGenerationProvider
        |       OpenAI / Google / Workers AI / other adapter
        |
        `--> InfraDriver.objects
                immutable media bytes
                immutable generation receipt
```

`InfraDriver` owns infrastructure guarantees. `MediaGenerationProvider` owns provider-specific generation behavior. The calling application domain owns the semantic decision that a particular asset may be generated and how the resulting asset may be presented.

## Why this is a separate service

Asset generation has concerns that should not leak into `insidefibre.com`, `PresentationServer`, `WorldStore`, or the cloud driver:

- asynchronous and potentially long-running execution;
- retries and provider failures;
- provider/model replacement;
- immutable generated bytes;
- generation provenance;
- deterministic job identity and deduplication;
- image/audio/video evolution;
- content and authority restrictions on what may be rendered;
- eventual approval/review workflows.

The service therefore does not make provider calls on the user-facing presentation request path.

## Contracts

### `AssetGenerationJob`

A job is a versioned, idempotent request to generate one asset:

```text
jobVersion
jobId
assetKind              image | audio | video
role                   caller-defined role
brief
  description
  constraints[]
inputReferences[]
outputObjectRef
receiptObjectRef
requestedAt
providerProfile
context                 opaque JSON owned by caller
```

`jobId` must be stable for the same semantic request. Reusing the same workflow instance ID with different input is a conflict.

`providerProfile` names a Fibre policy/profile, not a hard-coded cloud product or model. The execution receipt records the actual provider and model used.

### `AssetGenerationReceipt`

A completed workflow persists an immutable receipt independently of ephemeral workflow execution state.

Ready receipts contain:

```text
status: ready
objectRef
sha256
mediaType
width / height / duration
completedAt
generation
  provider
  model
  providerRequestId
  generatedAt
inputReferences[]
context
```

Unavailable receipts contain no fabricated object identity and record a reason.

Workflow retention and observability are operational concerns. They are not the permanent generation-provenance record; the receipt is persisted through `InfraDriver.objects`.

## Provider boundary

`MediaGenerationProvider` is intentionally outside `InfraDriver`.

Infrastructure portability and media-provider portability are different concerns:

```text
InfraDriver
  Cloudflare / AWS / GCP / Azure

MediaGenerationProvider
  OpenAI / Google / Workers AI / other media provider
```

The v0.1 provider contract accepts an admissible brief and returns bytes plus actual provider/model metadata. It is sufficient for the first still-image pass. Audio/video providers may require a later submit/poll extension before P6; v0.1 must not make a synchronous-still implementation a permanent constraint.

Provider credentials are provider secrets, not infrastructure-driver credentials.

## Thread Presentation adapter

Thread Presentation owns the first adapter:

```text
ThreadPresentationPacket
ThreadMediaPacket
PresentationProvenance
        |
        v
ThreadPresentationAssetPlanner
        |
        +--> eligible generation jobs
        `--> explicit deferred slots
```

The planner may use only the presentation material available for that slot. It must not query hidden Thread state merely to make a richer image.

### P2 Cần Thơ eligibility

For the existing golden Cần Thơ fixture:

- five `place` images are eligible from place presentation text;
- six `memory_reconstruction` images are eligible from autobiographical remembered content plus explicit uncertainty;
- `primary_portrait` is **deferred_missing_embodiment_brief** because #39 did not establish authoritative or approved embodiment for the candidate;
- voice is deferred;
- life-film/video is deferred.

This means the current packet produces 11 admissible still-image jobs and 3 deferred slots.

The planner must not solve a missing portrait brief by asking a model to invent a canonical face.

## Reconstruction briefs

A place brief must state that the output is generated reconstruction rather than documentary evidence and may use only the published place description as factual grounding.

A memory brief must preserve the distinction:

```text
historical event != autobiographical memory != generated reconstruction
```

Uncertainty from the memory packet must remain uncertainty. It cannot be converted into precise visual detail merely because an image model requires a prompt.

When no embodiment is supplied, reconstruction briefs must not establish a canonical facial likeness.

## Execution flow

```text
1. caller validates its source packet/projection
2. caller creates deterministic AssetGenerationJob
3. AssetGenerationService starts InfraDriver workflow instance
4. request path returns; no generation bytes are produced inline
5. workflow invokes MediaGenerationProvider
6. transient provider/runtime failure remains retryable workflow failure
7. successful bytes are SHA-256 addressed and written immutably
8. immutable AssetGenerationReceipt is written separately
9. caller receives/reads receipt
10. calling domain publishes its own update
```

For Thread Presentation, step 10 becomes a legal presentation `media.ready` or `media.unavailable` event. The asset service itself does not author presentation semantics.

A later presentation snapshot may incorporate the receipt into a new `ThreadMediaPacket`. The original snapshot is not rewritten in place.

## Cloudflare v1 mapping

The first deployment uses Cloudflare through the general `InfraDriver`:

```text
AssetGenerationService
        |
        v
InfraDriver.workflows
        -> Cloudflare Workflows

InfraDriver.objects
        -> R2

optional fan-out/backpressure
        -> Cloudflare Queues

provider adapter
        -> provider binding/API independently of InfraDriver
```

Cloudflare Workflows are a good fit because asset generation can become multi-step, retryable, or long-running. A future video provider may require durable sleeps/polling or approval. Queues remain useful for high-volume fan-out and backpressure but are not the semantic provenance record.

Cloudflare binding identifiers, workflow IDs, R2 keys, account IDs, and deployment credentials must not leak into Thread or presentation semantic contracts. Fibre object references remain stable application identities and the cloud driver maps them to provider-native resources.

## Storage and publication

Generated bytes are immutable objects. Regeneration creates a new job/output identity rather than overwriting an existing generated object.

The asset receipt is also immutable. This preserves:

- exact input references;
- provider/model used;
- generation time;
- byte digest;
- caller context;
- why a terminally unavailable slot was not produced.

The public viewer should receive a Fibre/application locator or object reference, never an `r2://` key or cloud-native object identity.

## Authority and causal status

This service is presentation/derived-asset infrastructure.

Generated media:

- does not become historical evidence;
- does not become autobiographical memory;
- does not become remembered meaning;
- does not become embodiment authority merely because a portrait looks plausible;
- does not feed back into Thread cognition as evidence unless a future explicitly authorized doctrine creates a separate legal path;
- may be deleted or regenerated without rewriting Thread life.

For H-v2 Genesis candidates, generated media remains `generated_reconstruction` inside an explicit fixture boundary.

The service therefore proves asynchronous generation, provenance, storage, and publication plumbing. It does **not** prove autonomous life, embodiment, identity, memory, or personhood causality.

## Failure semantics

Distinguish at least:

```text
retryable operational/provider failure
  -> workflow retries; no unavailable receipt yet

terminal unsupported capability / policy refusal / invalid brief
  -> unavailable receipt; no fabricated media object

successful generation
  -> immutable bytes + ready receipt
```

Do not convert a transient outage into permanent `unavailable`, and do not retry a deterministic policy refusal indefinitely.

The exact terminal-provider error taxonomy is still deferred for the first real provider adapter.

## Portability requirements

Every production InfraDriver implementation used by this service must prove:

- workflow start is idempotent for identical instance ID/input;
- conflicting reuse of an instance ID fails closed;
- workflow input is JSON/replay safe;
- immutable objects cannot be silently overwritten;
- stored digest identifies the bytes actually persisted;
- no provider-native resource ID becomes a Fibre semantic identity.

Every MediaGenerationProvider adapter must prove:

- it receives only the approved brief and references intended for it;
- actual provider/model metadata is returned;
- binary output has a declared media type;
- unsupported asset kinds fail without fabricated output;
- provider-specific response metadata cannot silently become Thread evidence.

## Current implementation status

Implemented on `agent/thread-presentation-milestones-v1`:

- general `InfraDriver.workflows.start/get` contract;
- in-memory workflow implementation and conflict semantics;
- `AssetGenerationJob` / `AssetGenerationReceipt` contracts;
- `MediaGenerationProvider` v0.1 contract;
- generic `AssetGenerationService` scheduling and workflow execution helper;
- immutable media + immutable receipt storage;
- Cần Thơ presentation asset planner;
- `media.ready` / `media.unavailable` presentation-event adapter;
- active tests for request-path asynchrony, immutable output/provenance, unsupported capability, packet-grounded planning, deterministic IDs, and event legality.

Not yet implemented:

- Cloudflare `workflows` driver;
- Cloudflare R2 object driver;
- a real image-generation provider adapter;
- terminal-vs-retryable provider error taxonomy;
- public media-serving endpoint;
- embodiment reconstruction brief / portrait generation;
- audio/video execution.

Those remain the next implementation steps; their absence must not be described as completed media generation.
