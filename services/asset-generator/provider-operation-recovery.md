# Provider operation recovery

Asset Generator separates an accepted asynchronous provider task from a completed `GenerationAttempt`.

This matters for providers such as Black Forest Labs FLUX, where one billable submission returns a task ID and polling URL before image bytes exist. Fibre must be able to survive a Worker or Workflow retry after that acceptance without buying a second nondeterministic image.

## Durable checkpoint

A resumable media provider may expose:

```text
startOperation(request)
resumeOperation(operationHandle)
```

`startOperation(...)` returns the exact secret-stripped provider request witness plus a secret-stripped provider operation handle. Before Fibre calls `resumeOperation(...)`, the portable Asset Generator runtime writes an immutable `ProviderOperation` checkpoint through `InfraDriver.objects`.

The checkpoint binds:

```text
jobId
full AssetGenerationJob SHA-256 digest
workflow/provider attempt number
providerProfile
provider adapter ID
exact provider request witness + digest
provider + model
provider request/task ID
opaque secret-stripped continuation data
acceptedAt
```

For BFL the continuation data is the provider-returned `polling_url`. The API key is never part of the checkpoint.

On a later Workflow retry, Fibre scans for a previously accepted operation for the exact job digest. If one exists, it reuses that operation's original attempt number and calls `resumeOperation(...)`; it does not call `startOperation(...)` again. A later successful `GenerationAttempt` therefore remains attached to the attempt that actually obtained the accepted provider task.

## Retry boundary

Three states are intentionally different:

```text
No accepted provider operation
  A provider call may be replayed only when the adapter can establish that the failure was pre-acceptance/replay-safe.

Provider accepted, checkpoint not durable
  Whole-job replay is forbidden. The portable failure reason is provider_operation_not_staged.

Provider accepted, checkpoint durable
  Polling/download failures may be retried because the next invocation resumes the same provider task.
```

This is separate from `providerOutputDurable`. A durable provider operation means Fibre can resume the same accepted task; durable provider output means the generated bytes themselves are already owned by Fibre and later credential/finalization work no longer needs the media provider at all.

## BFL FLUX

The current BFL profile uses `flux-2-pro`, the fixed FLUX.2 Pro endpoint selected for reproducibility. BFL's API is asynchronous: submission returns an `id` and `polling_url`; Fibre persists those before polling. Polling and delivery remain provider-adapter behavior, while checkpoint identity and persistence are provider-neutral Asset Generator behavior.

BFL credentials are deployment secrets. Local development uses:

```text
BFL_API_KEY=<your-bfl-api-key>
```

The adapter sends that value only in BFL's `x-key` request header. The job does not contain the key, and neither the provider request witness nor the operation checkpoint contains it.

No `BFL_MODEL` environment variable is required for the current profile. `bfl-flux-2-pro-v1` is the logical Fibre provider profile and the Cloudflare deployment maps it to the pinned `flux-2-pro` endpoint.

## Residual ambiguity

This checkpoint cannot make an external HTTP side effect and Fibre object persistence atomic across two independent systems.

If BFL accepts a submission but the response containing its task ID never reaches Fibre, Fibre has no accepted task identity to persist or resume. The current adapter therefore treats submission transport ambiguity as terminal rather than resubmitting. The BFL documentation used for this integration describes task IDs, polling URLs and webhooks but does not document a submission idempotency key that Fibre could use to close this final ambiguity window.

That residual case is a provider/API boundary, not a reason to weaken the durable checkpoint after an ID is successfully received.
